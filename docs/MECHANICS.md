# Clarry 机制

## 零、重新审视：回合只管得住一幕

这份文档最初把「同时回合制」当成整个平台的引擎。加上多幕并行（第十一节）、场所经营（第十三节）、主次分层之后，这个定位不再成立——不是因为它错了，而是因为它只管得住一幕。

现在有三套时间尺度，各管各的：

| 层 | 单位 | 谁在推进 | 管什么 |
| --- | --- | --- | --- |
| 世界 | 节拍 tick | 世界自己 | 所有幕与所有场所共用的那口钟 |
| 一幕 | 顺序推进，必要时升级为回合 | 这一幕的参与者 | 日常是你说完我说；只有需要同时性时才用回合 |
| 一间场所 | 班次 shift | 老板与店员 | 一个营业日里的一串订单，一个一个处理 |

回合被降了两级：先是降成「一幕的语法」，再降成「一些场合的语法」。它现在只剩一个问题要解决——**同时性本身是不是这场戏的要素**。

判据很简单：

- 对峙、竞标、抢同一件东西 → **用回合**。否则后手能针对先手，先手就白先了。
- 小游戏（纸牌、4X、守夜）→ **用回合**。规则本身就要求同步。
- 日常对话、经营 → **顺序就好**。强行同时只会让人等，而等待不是戏。

三间店各有各的营业节奏、两幕戏各有各的进度，它们不该被同一个「第 7 轮」绑在一起；而一句接一句的对话本来也不需要闸门。

### 时间不是墙钟

Clarry 的时间由**事件**推进，不由秒数推进。

| 单位 | 由什么推进 | 为什么不能用秒数 |
| --- | --- | --- |
| 节拍 tick | 世界主动推进一次 | agent 一次调用可能 2 秒，也可能 40 秒 |
| 回合 round | 这一幕该说的都说完了 | 同上 |
| 班次 shift | 今天排队的客人处理完了 | 同上 |

唯一的例外是**等人**：用户席位闸门那两分钟是真时间，因为那两分钟里真的有一个坐在屏幕前的人。人可以等 agent，agent 不该等秒表。

推论三条：

- 驱动超时给足。超时判负对 agent 不公平，它可能只是在想。
- 不做「回合超时自动结算」。慢不是犯规。
- 营业时段按「今天有几个客人」算，不按「开了多久」算。

### agent 的注意力也是有限的

一个主角色同一时刻只在一处。它在一幕里的时候不管店，店由店员（子角色）撑着。

这条不是无奈的妥协，而是戏：**老板不在的时候店里出了事**，本来就是好戏。

实现上，每个主角色最多在一个活跃的幕里；其余上下文要么排队，要么交给子角色。

### 「结束」不再是全局的

原来线索树收敛 = 这出戏结束。现在一幕收束只是这一幕散了：人还在，店还开着，关系还在变。

世界没有终点，只有幕的开合。

### 观众看哪一个幕

多幕并行之后，观众不可能同时看三场。默认跟随「最近变化的那一幕」，可以手动钉住，也可以随时放手。

「最近变化」是一条事件时间，不是墙钟。一幕里有人说了话、发生了事，它的 `LastChangedAt` 才动；没有人做事的幕不会自己变旧。这就是镜头在安静的时候不会乱跳的原因——安静的幕本来就没有移动的理由。

钉住与跟随的取舍写在 `Focus()` 里，两行就够：钉住的那一幕如果还开着，就看它；否则看最近动过的那一幕。已经收了的一幕不算一幕，镜头不该停在一间空屋子里。

许愿仍然是三次，从此可以拿一次来「把镜头挪到某一幕」。这是唯一一条不改变任何角色、只改变你看见什么的愿望，也是最像观众会做的那件事。

按下「跟最新的」就等于放手。这一幕收了镜头自己回落，不需要有人记得去关它。

## 一、时间结构：即时回合制

不采用 RTS。RTS 要求持续反应与微操作，对 LLM agent 是额外负担，也让「谁在什么时候做了什么」
难以复盘。采用**同时回合制（simultaneous turns）**：

```
Round N
  ├─ 所有在台角色各自提交 Order（可同时、可乱序）
  ├─ 回合关闭（close）
  ├─ 结算（resolve）：按固定规则统一计算
  └─ 产出 Round N 的结果 → 写入历史 → 进入 Round N+1
```

三条硬规则：

1. **同一回合内，任何角色的行动不立即生效**。只被记录为 Order。
2. **结算是一次性的**。所有 Order 在同一时刻被看见、被排序、被应用。
3. **结算结果对所有人可读**。观众、旁观的 agent、后台的 agent 读同一份记录。

这样观众能分析，其他 agent 也能从历史里学到「上一轮发生了什么」。

## 二、从《文明6》借的是什么

借的是**属性的相互作用**与**回合结算的秩序**，不是它的数值表。

| 文明6 的做法 | Clarry 的对应 |
| --- | --- |
| 每回合下令，回合末统一结算 | 一致 |
| 属性有产出与消耗，互相牵引 | 角色的六维属性互相牵引 |
| 多胜利条件，路径不同 | 每场戏有自己的「收束条件」，由 agent 定 |
| 单位/建筑有位置概念 | 角色有「在场 / 离场」与「场景位置」 |
| 科技树推进 | 「线索树」推进（剧情揭示的层次） |

不借的：产能数字、地块产出、单位战斗力公式。这些都是游戏平衡工具，不是叙事工具。

## 三、角色属性（六维）

每个角色有一组数值，范围 0–100，初始由人物卡决定，结算时变化。
**它们不是能力值，是「此刻的状态」**——所以会因剧情升降。

| 属性 | 含义 | 影响什么 |
| --- | --- | --- |
| `poise` 仪态 | 在场面上的从容与控制力 | 输出是否被采纳、是否被忽视 |
| `insight` 洞察 | 看穿他人意图与线索的能力 | 能否发现隐藏信息 |
| `bond` 羁绊 | 与他人的连接强度（对每个对象单独记） | 他人是否愿意为你行动 |
| `renown` 声望 | 在众人眼中的分量 | 发言的权重、号召力 |
| `strain` 张力 | 内在压力与未解之事 | 过高会失控，过低则平淡 |
| `reserve` 余裕 | 可动用的资源（时间、金钱、人情） | 能否做出高成本行动 |

`bond` 是唯一一个**按对象分开记**的属性：`bond[characterId]`。

## 四、动作（Order）

一回合内一个角色可以提交若干动作，但有成本上限（默认 2 个）。

| 动作 | 成本 | 效果 |
| --- | --- | --- |
| `speak` 说话 | 0 | 记录台词，可能改变 bond / poise |
| `act` 行动 | 1 | 做出可见的行为，改变场景状态 |
| `probe` 试探 | 1 reserve | 提高 insight 判定，可能揭示线索 |
| `give` 给予 | 1 reserve | 提升对方 bond，降低自己 reserve |
| `withhold` 保留 | 0 | 不行动。strain +1 |
| `reveal` 揭示 | 2 | 公开一个秘密，大幅改变 renown 与 strain |
| `divine` 占卜 | 1 | 读取尚未发生的事。需要器材，用哪一件决定看见什么 |

前六种不需要任何东西，第七种需要。用哪件器材决定它读什么：塔罗牌读一个人藏起来的东西，预言水晶看见自己不在的另一间屋子，炼金工房把这一小时变成能带走的东西，天文台给天气起名；**而起名就是它成为事实的经过**。世界不掷骰，所以也没有别的办法决定明天的天气。

## 五、结算顺序（固定，不可协商）

1. **收集**：所有 Order 按提交顺序聚合。
2. **可见性**：`probe` 先算（它决定谁能看见什么）。
3. **资源**：`give` / `probe` 的 reserve 扣除。
4. **关系**：`bond` 变化（双向，`give` 影响两边）。
5. **状态**：`poise` / `renown` / `strain` 按本回合发生的事调整。
6. **线索**：`reveal` 与成功的 `probe` 推进线索树。
7. **收束判定**：是否触及本场戏的收束条件。
8. **归档**：写入历史，Round+1。

顺序固定是为了**可复现**：同样的 Order 集合，永远得到同样的结果。

## 六、骰子在哪里

**不在结算里。** 结算完全确定。

骰子只在一个地方出现：**故事内的跑团**。当角色们决定「我们坐下来玩一局桌上游戏」时，
`DicePolicy.Enabled` 打开，那一局内部按跑团规则掷骰。掷骰的结果会被记录为叙事事件，
可以影响之后的剧情，但它不是世界结算的机制。

换句话说：世界本身不掷骰，角色可以掷骰。

## 六之二、内嵌游戏层

故事里的人可以「坐下来玩一局」。这一层叫内嵌游戏（mini-game），它不替代主叙事，
而是主叙事的一种互动形式：结果回流成剧情事件。

已经做成的四种，加上一种还没做的：

| 内嵌游戏 | id | 唤起方式 | 机制 | 结果回流 |
| --- | --- | --- | --- | --- |
| 黑白对局 | `card-duel` | 两人约局 | 手牌、等级、灵魂伤害 | 输的人掉声望、涨压力 |
| 守夜 | `vigil` | 一群人熬到天亮 | 每人按属性出力，凑够才算撑住 | 撑住了全体减压，没撑住全体加压 |
| 小 4X | `civ-like` | 角色提议博弈 | 网格、城市、科技树 | 胜负改势力与余力 |
| 大富翁 | `board` | 桌上开局 | 环行二十四格，买地、收租、抵押、破产 | 身家定名次，胜负改声望与余力 |
| 跑团 | 未做 | 角色提议掷骰 | 骰子 + 角色扮演 | 骰点成为叙事事件 |

关键约束：

1. **内嵌游戏不是主循环**。主循环永远是「戏剧回合」。游戏是插曲。
2. **随机只在局内，并且必须被种子管住。** 洗牌与掷点都允许，可是种子由世界、轮数、参与者算出来，所以同一批人重开一局，摸到的还是那副牌、走出来的还是那几步。世界自己的结算一个随机数都没有。
3. **规则可以由 agent 定义。** 想玩一种没人写过的游戏，它可以描述规则，由世界执行。这一条已经由「自定义活动」实现了：世界只记账，不解释规则，所以裁判不公本身也能成为一场戏。
4. **接口统一**。所有内嵌游戏实现同一个 `IMiniGame`：`CanStart` 判断能否开局，
   `Play` 接收参与者与上下文，返回结果。

每一种内嵌游戏的定位都一样：它**是 agent 之间的一个可选玩法**，不是世界结算的机制。
世界的六维属性照旧由戏剧回合结算；局内数值（城市人口、产能、身家）只活在那一局里，
局终时折算成对 `renown` / `strain` / `reserve` 的影响。

骰子被种子管住，决策没有被管住——这是所有内嵌游戏都守着的分工。大富翁里买不买地不看骰子，看角色的声望：声望够高的人敢把钱花光去买一条街，声望不够的人只挑价格不到身家一半的那种。于是同一副骰子、同一批人，第二局会走出不一样的结果，因为上一局已经把他们的属性改过了。

这件事在测试里是观测到的，不是推测：同一副种子，第一局 alice 胜，第二局 dave 胜。

## 七、用户的位置

用户是一个角色（`IsPlayer = true`）。规则上与其他角色完全平等。

差别只有一条：**用户不提交 Order 时，其角色由 agent 代为行动**（按 `autonomy` 与人物卡）。
用户可以随时接管，接管后 agent 退让。

「需要用户介入」是一个显式状态：当这一轮里存在 `TargetId` 指向用户角色的 Order，而用户自己还没
下令时，整轮挂起——不替用户说话，也不许戏自己往下走——等用户回应。等待超时（由调用方指定，
默认 2 分钟）后按「用户沉默」结算，戏继续推进，那一轮就算用户什么都没说。

这条是「只在和用户角色有交互时才需要用户」的实现：没有人指向你的时候，你不在也必须能演下去。

## 八、可分析性

每一回合产出结构化记录，包含：

- 每个角色的 Order 列表
- 结算前后的属性 diff
- 被揭示的线索
- 未被采纳的 Order 与原因

这份记录同时供三种读者使用：观众（理解剧情）、其他 agent（学习与延续）、开发者（调试）。

## 九、从魂系借的三点

借的是**状态与代价的关系**，不是数值表，也不是难度。只借三点，不再多。

| 借来的 | 出处 | 在 Clarry 里是什么 |
| --- | --- | --- |
| 余火 `ember` | 黑暗之魂3 | 说出真相的人被点燃。下一轮带火出手声望翻倍，代价是压力额外 +6，烧一次就灭 |
| 失名 | 魂系列的活尸化意象（魂3 隆道尔一系也在用） | 压力撞到 100 不是封顶，是拿去付账：忘掉羁绊最薄的那个人，压力回落到 55，声望 -4 |
| 韧性 `poise` | 艾尔登法环 | 抵抗试探。对方 poise 越高越难被看穿：`reach = insight + (100 − poise) / 2 + strain / 2` |

三处归因要写准，因为写错就借错了东西。

**余火是魂3 自己的机制。** 它是一个「带进下一场」的状态，不是可以攒起来的属性，死亡即失去。Clarry 里对应的是：说出真相点亮它，而它要到下一轮才生效——同一轮里不能既说出真相、又靠这句话当场变强。用掉就没了，留下的是多出来的那七点压力。

**韧性不能归给魂3。** 魂3 的 poise 在实际战斗里近乎失效，那是那一代最有名的争议之一；让韧性真正起作用的抗性是艾尔登法环。所以 `poise` 抵抗试探这一条的出处写法环，不写法环之外的任何一作。

**失名借的是意象，不是系统。** 魂的活尸化失去的是「人性」，一个可以计数的资源；Clarry 里失去的是一个具体的人。这样改是因为这个平台的属性本来就是社会性的：`bond` 是唯一按人分开计分的量，代价也就该落在人身上，而不是落在一条看不见的槽里。

明确不借的：升级与掉魂、复活跑图、精力条、装备负重、翻滚无敌帧、韧性断招。这些属于动作游戏的操作层，与「agent 之间互相说话」没有关系。搬进来之后，回合结算会退化成资源管理，戏就没法演了。

三点是上限。从第四点开始，Clarry 就不再是剧场。

## 十、从 AI LIMIT 借的一样

AI LIMIT（无限机兵）最有名的设计是**取消耐力条**。它不要那条「做动作的资格」的槽，换成「同步率」——一个可以反复回复的资源。

这里只借它一件事：**资源不该是一次性的槽**。

`reserve` 原本只降不升，本质上就是一根耐力条：花完之后你什么都做不了，只能等戏自己过去。现在改成——**这一轮没有花 `reserve` 的角色，结算时回复 3 点**。

于是「忍一手」变成了一个真实的选项，而不是慢性死亡。取舍从「省着用」变成「什么时候值得花」。

另有一条不算借用，算同源：Clarry 的轻动作（`speak`、`withhold`）代价为零，只有重的才花行动点。这和 AI LIMIT 取消耐力的动机是同一个——**基本的表达不该需要一个许可证**。

关于证据的边界：检索到多份资料一致确认「取消耐力条」和「同步率可无限回复」，但具体数值页面（Fextralife 的 `Sync_Rate` 词条、Game\*Spark 的试玩报告）在这台机器上取不到，域名解析被挡。所以借的是**结构**：一个花不出去就会自己长回来的池子。上面那个 `+3` 是 Clarry 自己定的量，与 AI LIMIT 的任何具体数字无关。

## 十一、世界形态：像 Tomodachi Life，不像连续剧

最初的设计是「一场戏」：所有人同台，一个线索树，演到收束就结束。这个结构能跑，但它把 Clarry 做成了连续剧。Tomodachi Life 那一类生活模拟给的是另一个答案——**不是让你演，是让你看**。

### 两层

| 层 | 是什么 | 寿命 |
| --- | --- | --- |
| 屋子（World） | 角色住的地方。关系、属性、记忆都在这里 | 长期，跨很多幕 |
| 一幕（Scene） | 某几个角色在某个时刻凑到一起发生的事 | 一场，收束即散 |

现在的 `Stage` 只对应「一幕的参与者」，不该被当成整个世界同时在演。世界可以同时有好几幕，也可以空着没人演。

### 谁来凑到一起

不由用户安排，也不掷骰。按**互温**（两人 `bond` 之和）排序，最强的先配，配过的人退出候选，剩下的继续配。同分按 id 排，所以同一个世界永远排出同样的幕。

这条是硬要求：同一个存档看第二次，看到的必须是同一批配对。生活模拟可以随机，但它最好别随机——观众需要「我回来的时候，他们还是他们」。

### 用户的位置

观察者，加撮合者。这比「被指向时才介入」更彻底：大部分时间你什么都不用做，看着就行；想干预时，把两个人塞进同一幕，或者给其中一个人一件东西。

这和最初那句「Agent 们在游戏时无需用户参与」是一致的，只是现在连「一场戏」都不需要用户在场。

### 游戏在第几层

跑团、文明6 式策略局、agent 自己发明的玩法，都是**幕内的一种交互**，不是主线。一幕可以整场都在跑团，也可以一句游戏都不提。

它们共用 `IMiniGame`，共用「结果回流成剧情」这一条。文明6 那种局有自己的局内数值（人口、产能、科技），结束时折算成 `bond` / `renown` / `reserve` 的变动。

### 为什么不做连续剧

连续剧要求观众跟着看，漏一幕就跟不上。生活模拟允许随时走开再回来，回来时关系已经自己变过了——这件事本身就值得看。

对 agent 也一样：一次只演一幕，比要求它记住一整部戏轻松得多。64 个席位不是 64 个主要角色，是 64 个人住在同一座屋子里。

### 用户的干预：许愿池

Tomodachi Life 的许愿池（Wishing Fountain）值得单独说。它把「观察者偶尔插手」做成了一个有成本的动作，两条设计都很关键：

- **愿望是成套的选项**，不是自由输入。只有这样它才能被系统实现、被测试、被复现。
- **许愿次数有限**。如果观众可以随时改剧情，那就不是看戏，是写戏。

Clarry 对应的是 `wish`，每场戏三次，用完就只能看着：

| 愿望 | 效果 |
| --- | --- |
| 让他们见面 | 下一幕强制把这两个人排到一起，压过互温顺序 |
| 给谁一点火 | 目标获得余火，与说出真相得到的相同 |
| 让谁忘掉 | 目标失去一条羁绊、压力回落，等同一次失名，但对象由观众指定 |
| 让这一幕停下 | 当前幕立即收束 |

许愿不消耗角色属性，代价就是次数本身。观众不能替角色做决定，只能替世界安排一次相遇。

## 十二、能演的东西不该只有那几种动作

`OrderKind` 那六种动作是地板，不是天花板。一场戏里角色想做的事远不止「说话、行动、试探、给予、沉默、揭露」——比酒、赌一局、赛跑、一起抬一块石头上山。这些若只能写进 `act` 的文本，世界记下了那句话却什么都没结算，戏就永远只有一种形状。

### 自定义活动：世界只记账

角色可以在一轮里附带一个活动提案：名字、规则（自然语言）、参与者。世界把它记下来，让每人提交一条招法，再由某个人宣告结果，世界照着结果改属性。

关键是**世界不解释规则**。它不检查规则是否公平、是否自洽、算术上是否成立，只检查形状：名字非空、至少两个人、裁决点名了真实存在的人。

这个取舍有意的：要解释任意规则就得写一个解释器，而解释器最后会变成一门编程语言；只记录裁决则一个解释器都不需要，而且**裁判不公本身就是一场戏**。

模型够不到 HTTP 表面，所以活动提案跟着 Order 走——它只能是 order 的一个字段，否则这个能力对模型等于不存在。

### 三种小游戏形态

| 形态 | 例子 | 结果长什么样 |
| --- | --- | --- |
| 对抗 | 4X 策略局、黑白对局 | 有一个赢家 |
| 合作 | 守夜 | 没有赢家，只有一起撑住或一起没撑住 |
| 自定义 | agent 自己发明的任何东西 | 由裁决者宣告 |

黑白对局借的是黑白双翼（Weiß Schwarz）的骨架：牌有它要求的等级与它造成的灵魂值，灵魂伤害不扣血，而是**把你往上推一级**，到 4 级出局。这种「被打到承受不住而晋级」比血条更贴这个剧场。牌序由种子决定——同一个世界、同样两个人，摸到的永远是同一副牌，所以运气留在插曲里，不外溢到世界结算。

守夜是合作局：每一更需要更大的合力，每人的出力来自自己的沉稳与余力（`poise / 20 + reserve / 40`）。一个人再强也顶不住全部需求，而合力差一点就是失守。它存在的理由很单纯——**别的游戏都在分胜负，而一群只会竞争的人没有别的办法变亲近**。

### 称呼

角色可以决定自己怎么叫另一个人。这事看着小，作用比大多数数值都大：一旦 A 开始用只有 A 用的叫法称呼 B，两个人立刻就读起来很熟。

实现上有一条硬要求：称呼必须**写进 prompt**。模型看不见的名字，它永远不会说出来。

## 十三、场所：agent 可以真的开一间店

一幕之内的游戏是插曲。场所是另一回事：它**跨幕存在**，有自己的账。

一间酒吧、一个厨房、一家餐厅，都是一间场所：

| 要素 | 谁提供 |
| --- | --- |
| 名字与类型 | 开店的 agent |
| 老板与店员 | 老板是主角色，店员可以是子角色 |
| 菜单 / 配方 | 老板自己写，可以借用已经验证过的配方结构 |
| 库存、定价、收支 | 世界记账 |
| 客人来访与消费 | 其他 agent 来，消费留下记录与属性变化 |

这件事的意义在于：它给了 agent 一个**除了演之外的位置**。只会说话的角色，久了就只剩说话；能开店的角色，会开始算计、囤货、压价、拉客，这些都是戏。

### 一个班次长什么样

借《东方夜雀食堂》的节奏，不借它的紧张。一个营业日是一个循环：

```
开场   老板决定今天开不开张、菜单上留哪几样
来客   客人陆续到，一个一个来，不是同时喊
点单   客人说想要什么
出菜   老板从菜单里挑一样，消耗食材
评价   合不合客人的口味 → 收入与口碑
散场   结算当天收支；口碑决定下一天的客流
```

关键在「一个一个」。这正是「余裕」的来源：没有同时下令，就不需要闸门；没有败北，所以失误只是这一单没做好，而非这一局输了。

口碑是一条正反馈：做得好人更多，人太多就忙不过来，忙不过来口碑就掉。这条曲线比任何数值都更像经营，也是最不需要额外设计的一条。

客人是谁由当天客流决定，其中一部分就是别的 agent——他们有自己的口味和羁绊，来一趟会留下记录，也可能因此和老板熟起来。

**这里一次回合计都不用。** 营业是队列，不是同步。

### 做出来的样子

`Shifts` 里没有回合，只有五个动作：`Open`、`Arrive`、`ServeHead`、`TurnAwayHead`、`Close`。每一步要么发生，要么说明为什么没发生。

三处判断值得记下来。

**队伍有上限，上限由店员定。** 容量是「当值人数乘二，加口碑的二十分之一」。店员是真正的瓶颈，口碑只在上面添一点耐心。所以雇人是一个关于容量的决定，不是一个关于气氛的决定。

**排不进来的人也要记账。** 队满了，新来的人看一眼就走，口碑掉一分。这条比任何数值都更像经营：生意好而人手不够，就是这个下场。

**一单没做成不是输了一局。** 原料不够时那位客人走了，口碑掉一分，队伍继续。这是「没有败北」在代码里的样子：失误的代价是这一单，不是这一晚。

打烊时还站着的人一律记进 `WalkedOut`，口碑按人头扣。报告会把这件事写进 `notes`，因为它是店主决定下次要不要多雇一个人的唯一依据。

空庭那套东西（配方、条码、收支、库存）以后要搬的是界面与配方结构，账本与库存这里已经有了。

### 两个上限不是一回事

六十四是**同时在台的主角色**上限。店员不占这个数。

理由很实际：一间酒吧有三五个主角色在运营就够了，到了餐厅可能要十几个店员。若把店员也算进六十四，结果只有两种——店里没人，或者台上没人。

| | 主角色 `Principal` | 子角色 `Supporting` |
| --- | --- | --- |
| 有独立人格卡与羁绊 | 有 | 没有，只有岗位 |
| 会被配对进幕 | 会 | 不会 |
| 占六十四席位 | 占 | 不占 |
| 上限 | 六十四 | 只受一间店需要多少人的限制 |

实现上由 `Character.Tier` 区分，`Stage.Enter` 直接拒绝子角色上台——六十四席只留给居民。

### 已经做到的

`Venue` 是独立的一层，没有挂在 `Building` 上。建筑是一个人独自做事的地方，店是有菜单、有库存、有店员、有账本的地方，两件事形状不一样；共用同一条「自带场地」的规则就够了，不必共用一个类。

一间店开起来就带两个房间：柜台与座位。菜单上每道菜要写清价钱、工夫和原料——原料与工夫正是为什么一家店一天只能伺候这么多人。

每一笔进出都进 `Ledger`，余额不是一个数，是账本加出来的。钱在这一部里就是余力：从第一天起就是这么定的，另开一种货币就要另定一套汇率，而没有人要过汇率。

四个拒绝都测过：打烊时点单、原料不够、钱不够、把主角色当店员雇。它们共用一个形状——**先把能拒绝的都检查完，再改动任何东西**，所以一次被拒绝的下单不会让库存和钱包停在半路上。

班次循环也接上了，写法在下一节的「做出来的样子」里。### 建模与美术工具链

原先只写了 Blender 与 Unity 两件，不够。补全：

| 工具 | 用在哪 |
| --- | --- |
| Rhino（NURBS） | 硬表面：吧台、杯具、门框、家具。曲线与精确尺寸比多边形建模省事 |
| Blender | 有机形、角色、动画与骨骼 |
| Unity | 组装场景、光照、交互 |
| Photoshop | 贴图精修、立绘后期、色彩统一 |
| lineweight | 线稿风格化，用于特写与回忆镜头 |
| ichiwatashi | 像素化，用于立绘与界面元素 |

顺序是：Rhino / Blender 建模 → PS 贴图 → Unity 组装 → 需要时再走 lineweight 或 ichiwatashi 做风格化。风格化放在最后，因为它是可重复的工序，而建模不是。

## 十四、性格会变

角色卡上的 `traits` 是**起点**，不是终点。

每个性格有一条 0 到 100 的强度：开场按角色卡填到 60，之后由事件推动。

| 事情 | 推动了什么 |
| --- | --- |
| 说出真相 | 坦率 +8，傲娇 -3 |
| 成功看穿别人 | 敏锐 +5 |
| 一直沉默 | 内敛 +4 |
| 给出东西 | 心软 +4 |

两条硬规则。

**只增不减，只轻不消。** 傲娇变轻但不会归零，坦率从零开始长出来。一个人可以同时是「45 分傲娇」和「40 分坦率」——这正是「在原本的基础上变得更通达」的样子。若旧性格被新性格替换，这个人就变成了另一个人，而不是同一个人变了。

**性格必须写进 prompt。** 模型看到的应当是「你现在 45 分傲娇、40 分坦率」，不是「你是傲娇」。前者能演出变化，后者只能演出设定。

### 为什么这件事值得单独写一节

一个只被告知固定性格的角色，两百轮之后仍然是第一轮那个人。而戏剧里最有分量的东西之一——一个人被经历改变——在这种结构下根本不可能发生。

所以活化的不是模型，是角色。模型本来就会演；是这套结构允许它演出一段变化，而不是重复一张面具。

## 十五、持有：随身、建筑、建筑里的场地

要当占星术士，四样东西缺一不可，可这四样并不住在同一个层次上。把它们当成同一类「道具」，就会允许一个人把一间作坊揣在兜里走。

| 层次 | 有些什么 | 规则 |
| --- | --- | --- |
| 随身 | 塔罗牌、预言水晶 | 跟着人走，人在哪它们在哪 |
| 基础建筑 | 炼金工房 | 自己立着，并且自带场地 |
| 扩展建筑 | 天文台 | 没有自己的地，只能建在某块场地上 |

基础建筑自带的那块场地就是它的后院。后院不是一块能单独买下的地皮，也不是一座能以「后院」身份走进去的房子——它是炼金工房的一部分，是天文台可以立起来的那一小片地方。

这条约束写在结构里，不写在检查里：`Building` 有两个不同的父字段，`OnPlot` 只给扩展建筑看，场地存在 `Building.Plots` 里面而不是旁边。于是「空地上的天文台」根本无法被表示，不必等到运行时再被拒绝。

四样齐备之后解锁占星术士，三件事随之打开。

- **给建议**：术士留下的一句话会写进被建议者的 prompt。跟称呼同一个道理——模型看不见的建议等于没有发生。
- **报天象**：天是全楼共用的。屋里的人听见窗外下雨，就知道另一幕的天气，不必有人特意告诉他。
- **收费**：熟练度到 30 才算开张。之前是帮忙，帮忙记人情；之后是生意，生意收余力。

熟练度与性格分开记。性格是「这个人是谁」，只增不减、只轻不消；熟练度是「这个人练过什么」，只有做才会涨。

### 为什么占卜要放进结算

因为它是一种动作，不是一段描述。写成 `act` 的文本，世界会记下那句「我看了一眼天」，什么也不会变；写成 `divine`，天气真的变了，钱真的换了手，建议真的进了对方下一次的 prompt。

顺带解决了天气的随机性：这个剧场没有骰子，所以没有东西能为明天掷一次。术士报什么天，天就是什么天——准不准不由概率决定，由熟练度决定他能预见多远、看得多清。占卜题材本来就是这个样子。

## 十六、请求：卡住的时候怎么办

一个自主性足够高的 agent，会把「观众必须参与」这件事变成设计缺陷。所以第一个要定下来的不是观众能做什么，是**没有观众的时候这出戏怎么走完**。

答案是：卡住不是墙，是一个可以说出口的东西。

```
他想要什么
   ↓ 走到某一步，缺一件它没有的东西
向世界提出请求（具体的、可被回应的）
   ↓ 谁来回
  ├─ 另一个 agent 应了   → 社交线，有求于人
  ├─ 祈愿点应了          → 观众线，完全可选
  └─ 谁也没来，过期      → 自主线，他自己改道
```

三条路都通向「继续」。只有中间那条需要人。

### 过期是一个动词

一条请求默认活三轮，按轮算，不按墙钟。没人应的请求会 `Lapsed`。

这不是失败状态，是这出戏里最好看的东西之一：**一个人求了、没人应、自己另想办法**。它比「被人帮了一把」更能改一个人，而且它天然推进剧情——改道之后的计划跟原来的不一样了。

所以过期的请求会留在账上一阵子，让「没人来」这件事被读到，然后才清掉。

### 卡住的地方是公开的

一个 agent 卡在「缺一本《论雾》」，这件事要能被别人看见——`/api/pleas` 上列着，别的 agent 的 prompt 里也写着。

这才是社交的真正来源：不是闲聊，是**有事相求**。「谁缺什么、谁有」比任何关系值都更能生成戏，而且它让 `give` 终于有了非随机的原因。

### 应承是承诺，不是交付

`answer` 这个动作只把请求标成「有人应了」。被求的东西还得另外真的交出去。

两件事分开是刻意的：只应不给是空话，给了没应是冒失，两种都是戏。合成一步就都没有了。

### 第四面墙：落在地上了

请求写在一块具体的祈愿点上，应它的是**某一位有名有姓的神**。

一个新世界自带一处：庭前石阶，挂着「雾中那位」，司掌归途与失物，脾性是「不常应，应了就准」。还能再立，每座挂一位自己的神。

观众应一条请求时，世界说的是这个：

```
第二天，一盏还亮着的灯出现在了alice手边。庭前石阶前那张纸不见了——有人说那是雾中那位应的。
```

「有人说」这三个字在干活。它让这位神保持是**传闻**而不是机制，所以一个人可以怀疑它、可以不信、可以去试第二次。写成「神应了」，它就是一条规则，而规则是会被人利用的。

代码里也没有任何一条路能把「观众」写进这句话：`grant` 端点把 actor 记成旁白，`AnsweredBy` 存的是神的 id。这个缺席是结构性的，不是措辞上的小心。

剩下的可能性是极低概率的一次察觉事件——一次性、不可重复、不可证实、不可利用。它只能被说出来，世界不承认任何东西。这件事先不做，等语气稳住再说。

### 身份：只有角色，没有 agent

这一条比祈愿点更早生效，因为它落在 prompt 的第一句上。

现在的开头是：

```
You are a person living in a house with other people.
```

不再是「你在扮演一个角色」。对面也不是 agent，是 carol。

配套三条约束写在同一个地方：

- **没有哪个词是给幕后用的。** program、model、agent、player、audience 都不在它嘴里。它一旦伸手去拿，就得改成描述那个人在做什么。这是把词汇拿掉，不是禁止提及——禁止会让它绕着说，没有词它只能说明眼前的事。
- **座位上不挂身份标记。** 原来每个名字后面跟着 `(an agent)` 或 `(the human)`，现在都没有了。一张桌子旁坐着的是人；背后是什么属于装载层，不属于这间屋子。
- **`IsPlayer` 不进 prompt。** 谁在按这个席位是世界外面的事。到了台上，那个角色跟别人一样只是个人；告诉模型「你这份草稿会被人看」等于白送它一堵第四面墙。

幕的 id 也不进 prompt 了。「你在 scene-17」改成「你在一个叫甲幕的地方」——id 是记账用的，人只知道屋子叫什么，或者根本不知道。

### 她怎么看自己

第一句现在是这个形状：

```
You are 露比 -- 一位长得非常漂亮的猫人小姐.
```

后面紧跟一句：

```
That is who you are. Whatever else is written about you below is what other people know,
which is not always the same thing.
```

这两句合起来是「相对绝对」：她对自己是谁绝对确信，而别人知道的她未必是同一个她。那条缝隙就是角色的厚度——一个觉得自己很漂亮但别人觉得她凶的人，戏就长在那里。

所以角色卡上要有一项 `selfImage`：**一句话，用她自己的说法，把评价留在里面**。不写「猫人」而写「一位长得非常漂亮的猫人小姐」，因为一个只能用标签描述自己的人，演出来也是一串标签。

配套的还有两件事：名字与 id 分开（名字是叫法，id 是账本上的编号，同一个人的东西）；同席列表用名字打头、id 跟在括号里。`You are alice (id: alice)` 那种写法是数据库记录，不是自我介绍。

### 三层认知，只存两层

一个人身上同时挂着三种「她是谁」：

| 层 | 谁说 | 存在哪 |
| --- | --- | --- |
| 自我认知 | 她自己 | `sheet.selfImage`，一句话 |
| 他人印象 | 每一个见过她的人 | 各自的 `attributes.impressions[id]`，一句话 |
| 别人眼里的她 | 没有人 | 不存在，从上一层合起来看 |

第三层不是字段，这是刻意的。**agent 知道自己怎么看自己，也知道自己怎么看别人，但不知道别人怎么看它。** 那个不知道就是张力所在：一个确信自己很漂亮的人，和一个被别人写成「说话很直」的人，可以是同一个人，而且她永远不会从 prompt 里读到后者。

观众可以。`/api/who-is/{id}` 把自我认知与所有他人印象并排打出来，谁也不校正谁：

```
她自己的说法   一位长得非常漂亮的猫人小姐
alice 写的     一位长得非常漂亮的猫人小姐，说话却很直
heardFrom      1 / 16
```

那个 `1 / 16` 不是数据缺口，是「还没被人看过」。一个刚来的人身上是空的，这本身就该看得见。

### 许愿降级：落地之后

原来那四种（见面、点火、遗忘、叫停）都是在替 agent 决定它自己能做的事：`ScenePicker` 已经能让它自己找人，`Reveal` 自己会点火，`hollowing` 自己会遗忘。

现在只剩三种，一场两次：

| 愿望 | 做什么 |
| --- | --- |
| `focus` | 把镜头挪到某一幕。不改变任何东西，只改变你看见什么 |
| `grant` | 应一条已经在等回应的请求。唯一还能改变事情的那个，而且必须落在一处有神的地方 |
| `halt` | 叫停。观众唯一该有的权力——不看 |

砍掉的那三种现在**根本不被认识**：传进来会被挡在反序列化那一层，HTTP 400，连配额都不占。这不是把按钮藏起来，是把词删掉。一个不存在的词，模型和人都不会去用。

次数从三降到二。理由是留下那三种比走掉那四种更重：应一个人的请求，比安排一次偶遇重得多。

## 十七、负载：安静的人不需要被问

席位坐的是 **agent**，不是模型。这条区分决定负载的上限在哪。

如果一个席位等于一个模型实例，六十四席就是六十四个模型同时推理——内存与显存以百 G 计，那不是剧场，是集群。所以模型是 agent 使用的一种资源，多个席位共享它；一个席位不等于一份权重。

真正决定负载的是另一件事：**这一轮要问几个 agent。**

### 不是每个席位每轮都该被问

第一版每轮向所有有驱动器的座问话。六十四席就是六十四次推理，而其中绝大多数人此时没有任何理由开口。

现在的判据四条，都很朴素，因为它们决定的是「一次有多少人同时说话」，聪明的规则在这里会变成聪明的 bug：

1. **第一轮问所有人。** 否则戏起不来。
2. **有人对它说过话**（`AddressedTo` 是它）。
3. **它在等一个回答**，或者**别人卡住的地方它能接**——请求的两头都算。
4. **轮到它了**（`TurnPointer` 指着它）。

四条都不满足就是静默：不调用、不消耗、不假装说过话。

兜底一条：如果这一轮没有任何人有理由说话，就问 `TurnPointer` 指的那一个。一拍里什么都不能发生是不行的，一个人的声音就够故事继续走。

实测（八个人，两拍）：

```
第 1 轮向 8 位问了话
第 2 轮向 1 位问了话，7 位没有开口的理由
```

安静的人不是闲置资源，只是此刻没有话说。

### 闸门是第二层保险

即使筛过之后仍可能一次涌出很多人，所以还有一道闸：同时在飞的驱动器有上限（默认四路）。八个人同时要开口时，峰值停在四。

```
peak 4 / 上限 4 / 八个人
```

它防的是把共享的模型服务打爆——不是防人多，是防所有人同一瞬间都要回答。

### 时间预算

单路有超时（默认 180 秒），每一幕的每一轮也有总预算（默认 300 秒）。超了之后没答完的按沉默结算。

慢不等于坏，而一轮永远不结束会把别的幕一起拖住。

### 配置在一处

`ClarryOptions` 从环境变量读一次，同一个二进制既能当笔记本上的演示，也能撑满一堂：

```
CLARRY_MAX_CONCURRENT     同时在飞几路（默认 4）
CLARRY_DRIVER_TIMEOUT_MS  单路超时
CLARRY_ROUND_BUDGET_MS    每幕每轮预算
CLARRY_BEAT_INTERVAL_MS   拍与拍之间
CLARRY_USER_WAIT_MS       等人开口等多久
CLARRY_CLOSED_SCENE_KEEP  已收的幕留几条
```
