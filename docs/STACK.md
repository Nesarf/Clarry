# Clarry 技术栈与边界

## 一句话

核心是 C#；Rust 负责热点；Java / Lua / Ruby 补 C# 的缺口；js / ts / py 只待在工具层与前端，不进核心。

## 分工

| 语言 | 位置 | 为什么是它 |
| --- | --- | --- |
| C#（.NET 10） | 领域模型、回合结算、HTTP 表面、状态机 | 一个语言同时给出强类型、async 与可用的 HTTP 栈，并且能和 Unity 共享同一套模型 |
| Rust | 上下文组装、token 预算、高并发 I/O | 这一段的时间与内存是直接成本，而模型调用按 token 计费 |
| Java | C# 生态缺某个成熟库时 | 解析器、协议库、老牌工具大多有成熟 Java 实现，不值得自己重写 |
| Lua | 可选的活动逻辑 | 嵌入式脚本，小、稳、沙箱友好；给愿意写规则的 agent 留一扇门 |
| Ruby | 文本处理与胶水脚本 | 文本处理顺手，写一次性的东西快 |
| js / ts / py | 舞台前端、DSH 插件、一次性脚本 | 只在这些地方。它们是轻量语言，用多了工程会松 |

## 纪律一：Rust 是热点的归宿，不是起点

在不知道热点在哪之前把东西写进 Rust，就是把「可能慢」当成「确实慢」，然后为一处不存在的瓶颈付上跨语言调试的代价。

正确顺序：

1. **先计量**。每轮每人喂进去多少 token、每个组件花多少时间。
2. **数据指向哪里，才把哪里搬进 Rust**。
3. **搬的时候选边界**。每次调用要过几百 KB 数据，走进程边界就不划算；调用很碎、数据很小，边界反而比 FFI 省事。

## 纪律二：token 预算先于任何优化

这是最容易失控的一笔成本：六十四个 agent 同时下令，每人一份 prompt。

一份 prompt 通常包含角色卡、六维、称呼、在场者、最近约二十四条历史、本轮预算。其中**历史那部分会随幕变长而线性增长**——这是唯一会自己膨胀的一段。

所以第一步不是换语言，是给上下文定预算：

- 每人每轮一个固定的 token 上限。
- 超了就裁：先砍与本人无关的历史，再砍更早的，最后才压角色卡。
- **裁剪规则必须确定性**，否则同一份存档跑两次会喂出两份不同的上下文，前面的「可复现」就全废了。

有了预算和计量，才知道 Rust 该不该上、该落在哪一段。

## 纪律三：只有一条契约面

语言之间只有一个接口：**HTTP + JSON**。除 Rust 可能走 FFI 之外，其余都走这条线。

不这样做的后果很具体：三种语言各自持有半份状态，出了问题要靠猜是谁改的。

## 不许越界的地方

- **领域规则不许落到脚本层**。回合结算、属性变化这些一旦散进 js/py，就再也没法完整测试。
- **前端不许持有游戏状态**。舞台只读一份世界快照并画出来，关掉它世界照常转。
- **不许为某个语言单独复制一份模型**。共享模型是这套架构里最贵也最值钱的东西。
