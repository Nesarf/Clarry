# 仓库、工作区与发布

## 三个数字，三件不同的事

| 名字 | 上限 | 指的是什么 |
| --- | --- | --- |
| 版本控制 | 500 MB | git 里真正存下来的东西 |
| 工作区 | 30–60 GB | 这块盘上 `D:\Clarry` 的总占用 |
| 单版本 release | 5 GB | 交到别人手上的那一个包 |

三个数字不能混。最常见的事故就是把它们当成一回事：以为「仓库能到 60 G」就意味着可以往 git 里塞 60 G 的 `.blend` 和 `.psd`。那样做的后果很具体——第一次克隆要几小时，而且 git 对二进制大文件几乎没有好办法，改一次就多存一整份，六十个版本之后仓库会自己爆掉。

## 什么进版本控制

**进**：源码、文档、脚本、schema、设计文件（`design/PLAN.json`）、像素立绘与生成它的脚本。

**不进**：`bin/`、`obj/`、建模源文件（`.blend` / `.3dm` / `.psd`）、未压缩贴图、构建产物、数据目录（`world.json`、`memories.db`）、本地缓存。

判断标准只有一条：**能不能从别的东西重新生成**。

- 能重建的（编译产物、下载的依赖、生成的贴图）不进版本控制。
- 不能重建的（手写源码、手调的设计文件）必须进。
- 建模源文件两边都不属于：它既不能重建，也不该塞进 git。它躺在工作区里，靠另外的方式备份。

## 工作区为什么能到 60 G

因为它要同时容纳这些「过程」而不是「成果」：

- 建模源文件（Blender / Rhino / PS 分层）
- 中间渲染与烘焙产物
- Unity 的 `Library` 与构建输出（这一项单独就能吃掉十几 G）
- 若缓存落在工程内的 NuGet 与 pnpm 目录

D 盘目前只剩 133 GB。工作区涨到 60 G 之后还剩 73 G，够用但不宽裕。所以需要的是**能按目录看体积的工具**，而不是等满了再找是谁干的。

## release 里放什么

5 GB 是硬上限，不是目标。预算表：

| 项 | 预算 | 现状 |
| --- | --- | --- |
| 服务端（.NET 自包含） | 200 MB | 尚未发布 |
| 客户端（若做 Unity） | 1.5 GB | 未开始 |
| 像素立绘与表情差分 | 200 MB | 目前 27 MB |
| 音频 | 500 MB | 暂无 |
| 场景与贴图（压缩后） | 2 GB | 暂无 |
| 余量 | 600 MB | 留给意料之外 |

三条规则：

1. **只放运行需要的东西**。源码、设计文件、建模源、测试脚本一概不进包。
2. **贴图压缩后才进包**。分层 PSD 留在工作区，永远不进 release。
3. **超预算就砍场景，不砍立绘**。立绘是角色的脸；场景可以少几间，人脸不能少。

## 检查

`scripts/release-size.ps1` 量三样：工作区总量、可发布产物的体积、以及按目录排出来的超限项。

它不猜，只报实测数字。任何一次 release 之前都先跑它，看到超了就先处理，而不是打包之后才发现。
