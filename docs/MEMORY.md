# Clarry 记忆

## 为什么现在这套不算记忆

眼下 agent 的「记忆」是 `World.History` 里最近十六条。它有三个毛病：

1. **共享的**。所有角色读同一份，分不清「我经历的」和「我听说的」。
2. **会断**。超出十六条就丢，而一场戏可以有一百轮。
3. **不分轻重**。一句客套和一个说出口的秘密，在它眼里一样重。

更麻烦的是，它和人设完全无关：一个谨慎的学者和一个粗心的诗人，记住的东西本该不一样。

## 一条记忆

| 字段 | 含义 |
| --- | --- |
| 属于谁 | 这是谁的记忆，不是世界的 |
| 看见了什么 | 内容，一句话 |
| 关于谁 | 可选，涉及另一个角色时填 |
| 有多重 | 权重，0 到 100 |
| 什么时候 | 发生的时间 |
| 还记得多少 | 经过衰减后剩下的权重 |

权重不是写死的常数，它由事情本身决定：`reveal` 与成功的 `probe` 重，日常寒暄轻。这一条和回合结算已经算出来的东西一致，不必另开一套。

## 人格怎么细调

人格不该只是描述，它该改变这个人**记得住什么**。从 `sheet.traits` 推出一组参数：

| 参数 | 作用 |
| --- | --- |
| 衰减 | 每轮乘多少。谨慎、好奇的人掉得慢；健忘、粗心的人掉得快 |
| 敏感度 | 权重加成。敏感、敏锐的人对同一件事记得更重 |
| 容量 | 最多留多少条。直率的人留得少，因为他不存细节 |
| 召回数 | 每轮想起几条。想得细的人想起得多 |

于是同一个事件，在三个人身上留下三种痕迹——这本身就是戏。

## 为什么不放在一个文本文件里

因为要问它的问题不是「全文是什么」，而是：

- 这个角色关于那个人的记忆，最重的六条是哪几条？
- 哪些记忆已经衰减到该丢了？
- 这一轮一共写了多少条？

这些问题在结构化存储里是一次索引查询，在一个越来越长的 JSON 里是一次全量解析加上一遍手写筛选。六十四个角色、每人几十条、跑几百轮，那个文件会变成谁都不敢碰的东西。

**SQLite** 合适：嵌入式、零配置、单文件但带索引与事务，而且不需要另起一个服务。

分片 JSON（每个角色一个文件）是过渡方案，不是终点：它解决了「单文件太长」，没解决「怎么按权重查」。

## 召回

每轮给某个角色组 prompt 时，从记忆里取：

- 与他有关的（涉及他的）优先
- 权重高的优先
- 同权重取更新的

取出的条数由人格的召回数决定，并计入每轮的 token 预算。

**召回必须确定性**：同一个世界、同一个角色、同一轮，取出的必须是同一批记忆。否则前面所有「可复现」都白做。

## 遗忘是功能

记忆会衰减，低于阈值就删掉。这不是为了省空间，是因为**遗忘本身有意义**：

- 一段关系变冷，往往是从「他记不清你上次说过什么」开始的
- 某人记得你随口的一句话，比任何数值都更能说明他在意

所以衰减参数要能被看见、能调，而不是藏在实现里。
