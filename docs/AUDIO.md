# Clarry 音频

## 四段，各用各的工具

音频不是一个「用哪个软件」的问题，是四段不同的事。

| 段 | 做什么 | 用什么 |
| --- | --- | --- |
| 一 创作 | 写出音乐与音效 | MuseScore 4（谱）／FL Studio 20.7（电子与声音设计） |
| 二 统一包装 | 响度、真峰值、首尾裁剪、采样率 | Adobe Audition 2024 或 FL Studio，二选一，全项目只用同一种 |
| 三 转码 | 压成发行格式 | ffmpeg |
| 四 集成 | 事件、随机、随状态变化 | 清单驱动（默认）；Wwise（要交互音频时才上） |

第二段是这套流程里最容易被跳过、也最不该跳过的一段。三个不同来源的音频（谱子渲染的、FL 做的、TTL 合成的）如果不在出口处统一，进游戏之后就会出现「过场很响、日常很轻」这种没法靠音量条解决的问题。

## 统一包装的规格

一次定死，之后所有音频都按这个产出：

| 项 | 值 | 为什么 |
| --- | --- | --- |
| 采样率 | 48 kHz | 与游戏常用一致，避免重采样 |
| 源位深 | 24 bit | 留出母带余量 |
| BGM 响度 | −16 LUFS | 能被语音压住，又不至于听不清 |
| SE 响度 | −18 LUFS | 音效不该比音乐响 |
| 语音响度 | −16 LUFS | 与 BGM 同级，靠 ducking 让位 |
| 真峰值 | −1.5 dBTP | 防削波 |
| 发行格式 | OGG Vorbis（音乐）／OGG 或 Opus（音效） | 体积与质量在 500 MB 预算内最划算 |

响度用 ffmpeg 的 `loudnorm` 做两遍：先测量，再按测量值应用。一遍动态归一化会压掉音乐的动态，游戏音乐不该被压成一条直线。

## Wwise：用在设计期，不进发布包

本机这套 Wwise 没有许可证。这不是技术问题，是授权问题，而且它决定了 Wwise 能用在哪个阶段。

**结论：用它的组织能力，不用它的运行时。**

- **设计期**：用 Authoring 建事件、分组、试听、做随机容器——这部分 Wwise 免费，且它的组织方式比一堆文件名可靠。带 **WAAPI** 和 `WwiseConsole.exe`，意味着这件事可以由程序驱动，不必手点界面。
- **发布期**：release 里只放 OGG 文件加一份清单，不打包 Wwise 运行时。**发布包不依赖 Wwise SDK，就不受其授权约束。**

什么时候才需要破这条：当真要做 RTPC 驱动的动态混音（比如压力越高、弦乐越紧）时，才必须打包运行时。那一刻之前，先解决许可证，而不是先写代码。

清单驱动的最小方案长什么样：

```json
{
  "bgm": { "quiet-night": { "file": "bgm/quiet-night.ogg", "loop": true, "lufs": -16 } },
  "se":  { "ui-click": { "file": "se/ui-click.ogg", "lufs": -18 } }
}
```

够用，可测，而且换中间件时不用改游戏代码——只换播放层。

## 预算

上一节的总预算里音频占 500 MB。按 OGG 算，这够：

- 20 首两分钟的 BGM（约 1.5 MB/分钟 → 60 MB）
- 300 个音效（平均 30 KB → 9 MB）
- 大量余量留给语音与后期追加

真正吃预算的从来不是音频，是场景贴图。所以音频这一块不必省。

## 检查

`scripts/audio-master.ps1` 做第二段与第三段：把一个目录里的 WAV 按规格统一响度、裁掉首尾静音、转成 OGG，并报告每个文件的处理前后响度。

它不作曲，只保证出口统一。
